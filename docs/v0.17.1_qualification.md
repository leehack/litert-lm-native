# LiteRT-LM v0.17.1 qualification preparation

Status: prepared compatibility change; **not a qualified runtime update**.
No release, workflow dispatch, qualification pin, or downstream consumer pin is
changed by this patch. Windows DXIL repair remains on a separate branch.

## Exact input and artifact blockers

As verified on 2026-09-18, upstream `v0.17.1` resolves to
`5e58e9a0aef7abf7091207a8b1d1063a1c800f08`, one commit after consumed source
`e9fd8c53ff968071774206163027dd84bedfe925`. The release was published
2026-09-16T19:59:09Z. Its notes reference a different commit,
`f300c4fdc28b4770c61ae93d24f3f601cfcd19f6`; the FC parser patch is identical,
but qualification must use the actual tag commit.

The only production changes concern integer-specific FC/Python grammar rules,
FC parsing into i64 before f64, and integer accessors across the Rust/C++ JSON
bridge. C headers, ASR sources, WORKSPACE/Cargo dependencies, and prebuilt inputs
are unchanged. This does not establish fixes for Windows DXIL, Qwen latency,
or the GGUF typed-tool-result exception.

The exact tagged `runtime/components/constrained_decoding/llg_fc_tool_calls_test.cc`
has an extra duplicated expression at line 652. Compiling the unchanged test
fragment (lines 611–706, with fixture stubs) produces `extraneous ')' before ';'`
at 652:100. This is a test-source defect, not a production parser build failure.
New examples at lines 657 onward also use `<|tool_call>` delimiters whereas
`GetDefaultFcOptions` at lines 182–191 uses `<start_function_call>`. Preserve the
original failure and use an explicitly reviewed test repair before relying on
that upstream test target; no upstream source was silently repaired here.

## Compatibility preparation

`prebuilt_overrides.py` previously selected the Android Dawn correction only
through v0.17.0. Explicitly retain the same two checksummed arm64/x64 overrides
for v0.17.1, whose Dawn inputs are unchanged. Do not generalize to unknown future
versions or retire the override without matching device evidence.

Version-floor tests cover unchanged stream/ASR exports and v0.17.1 build options
for all nine targets: Android arm64/x64, iOS arm64/simulator-arm64, Linux
arm64/x64, macOS arm64/x64, and Windows x64. These are command-selection tests,
not nine successful builds.

Existing guarded SentencePiece 0.2.2 BPE-NUL and iOS framework/sampler patches
remain applicable. Exact-source WORKSPACE and sampler preparation succeeded;
patch dry-runs passed against the unchanged pinned LiteRT and SentencePiece
files. Existing source-identity, archive/hash, publication, and scheduling
security gates remain unchanged. Linux dependency/RUNPATH handling and ASR ABI
remain intact; no Windows loader fix is imported into this branch.

## Bounded local evidence

- Tooling: 183 tests, OK with one platform-dependent skip; 21 diagnostics tests
  pass. Lifecycle tests could not run: all 25 stop at the Bash 4+ prerequisite
  on this host (system Bash is 3.2; no Homebrew Bash is installed). This is an
  environment limitation, not successful lifecycle qualification. Existing
  lifecycle/scheduling security checks remain unchanged and must run in CI.
- Exact upstream Rust parser sources: six FC parser tests and seven shared
  accessor tests pass using upstream-locked direct dependency versions.
- Compiled exact production FC/Python grammar generators with local C++20
  libraries; llguidance 1.3.0 accepted/rejected all 48 numeric controls using a
  byte vocabulary. Integer rejects fractions/exponents; number retains them;
  malformed forms and wrong types reject. This does not test model tokenizers.
- Compiled exact production `parser_common.cc` against the generated cxx 1.0.149
  bridge and Rust parser library. FC/Python/JSON preserve `9007199254740993`,
  i64 limits, ordinary integers, and decimal float distinctions. Of 27 probes,
  26 parsed and preserved the checked representation; Python `1e3` rejected.
  The unchanged Python lexer accepts decimal FLOAT but has no exponent rule,
  an existing mismatch with the Python number constraint grammar. Retain that
  failure; do not count it as a passing end-to-end number case.

No fresh bridge-enabled v0.17.1 runtime was built. Actual public-Dart tool
arguments, native ASR, Qwen, and Gemma model execution on the candidate remain
NOT_RUN. Old-runtime or unchanged-asset smokes cannot fill these evidence gaps.

## Proposed qualification route (requires separate approval for dispatch/pins)

1. Keep the compatibility carry-forward as a narrow owner PR candidate.
2. Obtain an explicit upstream-test repair for the syntax/delimiter defects and
   decide how the pre-existing Python exponent mismatch affects acceptance.
3. Prefer exact-source bridge builds for the runtime fix. If official Apple
   wrappers are required by the shipping layout, wait for corrected/provenanced
   upstream assets or separately review a source-built Apple packaging route;
   do not bypass the official-asset checks or copy old evidence.
4. After approved qualification-input changes, run the existing nine-target
   build/export/dependency/package gates and fresh Linux/Windows/macOS CPU ASR.
5. Run actual public tool arguments (including integer/number controls and a
   deterministic >2^53 parser case), Qwen tokenizer/generation, and Gemma CPU
   generation using the newly built candidate and exact model/config hashes.
   Keep generated-model choices separate from deterministic parser assertions.
6. Retain physical GPU and Windows DXIL qualification as separate obligations.
   No publication or downstream adoption until applicable gates are satisfied.
